## 5. Proven Root Cause

### Primary Root Cause: **Canonical Stop Proximity Grouping Bug**
- **Location**: [`tracking/services/route_finder.py`](file:///c:/Users/NAVEET/Documents/TRAVLE%20DOTS/tracking/services/route_finder.py#L250-L252)
- **Exact Code Line**:
  ```python
  250: is_close_proxy = haversine_distance(s1.latitude, s1.longitude, s2.latitude, s2.longitude) <= 0.15
  251: if is_name_match or is_close_proxy:
  252:     self.canonical_group[s1.id].add(s2.id)
  ```
- **Why it Fails**:
  The condition `is_close_proxy` merges any two distinct bus stops into the same `canonical_group` if they are physically within 150 meters of each other, **even when their names are completely different** (e.g. `Shiridi nagar` vs `Shanti Nagar`).

### Secondary Root Cause: **Validation Pipeline Endpoint Over-Permissiveness**
- **Location**: [`tracking/services/route_finder.py`](file:///c:/Users/NAVEET/Documents/TRAVLE%20DOTS/tracking/services/route_finder.py#L478-L480)
- **Exact Code Line**:
  ```python
  479: if final_drop_id not in dest_canon and final_drop_id != dest_stop.id:
  480:     return False
  ```
- **Why it Fails**:
  `validate_and_finalize_journey()` permits the final drop stop to be *any* stop ID present in `dest_canon`. When `dest_canon` contains physically nearby stops with different names, the algorithm returns a journey ending at a different stop than the requested `dest_stop.id`.

## 6. Fix Plan (No Changes Implemented)

### Files Needing Modification:
- [`tracking/services/route_finder.py`](file:///c:/Users/NAVEET/Documents/TRAVLE%20DOTS/tracking/services/route_finder.py)

### Functions Needing Modification:
1. `TransportGraph._build()` (Lines 242–253):
   - **Fix**: Remove `is_close_proxy` from `canonical_group` construction, or require BOTH `is_name_match AND is_close_proxy`. `canonical_group` must ONLY group stops that represent the same physical station complex under the same or nearly identical name (e.g. `CBT` vs `CBT Hubballi`).
2. `validate_and_finalize_journey()` (Lines 473–480):
   - **Fix**: Require that `final_drop_id == dest_stop.id` (or strictly name-equivalent canonical stops). If a transfer journey drops the passenger at a nearby stop `s2` within walking distance of `dest_stop`, it must explicitly render a final walking transfer leg `s2 ➔ dest_stop` rather than claiming `s2` is `dest_stop`.

### Safest Implementation Approach:
- Separate **Canonical Name Grouping** (`canonical_name_group`: stops sharing identical/normalized names) from **Spatial Transfer Proximity** (`walking_transfer_neighbors`: stops within walking distance $\le 500\text{m}$).
- Ensure that the boarding stop and final drop stop of a journey ALWAYS match `source_stop.id` and `dest_stop.id` (or their exact name aliases).

### Possible Side Effects:
- Zero side effects on direct routes.
- 1-transfer routes that require a final short walk ($\le 200\text{m}$) from the drop stop to the destination will cleanly show the final walking leg instead of mislabeling the drop stop.

### Unit Tests to Add:
- `test_exact_destination_stop_matching`: Asserts that when `destination="Shiridi Nagar"` is requested, the returned final drop stop name is strictly `"Shiridi nagar"` and NOT `"Shanti Nagar"`.
- `test_canonical_group_different_names`: Asserts that stops within 150m with different names (e.g., `Shiridi nagar` vs `Shanti Nagar`) are NOT placed into the same `canonical_group`.
